Системы, которые следует покрыть трейсингом:

1. Internet Shop
2. Shop API
3. CRM API
4. MES API
5. Messages Queue (RabbitMQ)
6. Shop DB
7. MES db
8. 3d files storage

Места, где заказ может «сломаться» или зависнуть:

1. Shop API -> Shop DB - ошибка при сохранении заказа.
2. Internet Shop -> Shop API - ошибка при отправке 3D-файла.
3. Shop API -> 3d files storage - ошибка загрузки файла.
4. CRM API -> Messages Queue - потеря сообщений о новых заказах.
5. Messages Queue -> MES API - сообщения не доставляются на производство.
6. MES API -> MES db - ошибка при назначении заказа оператору.

Список данных, которые должны попадать в трейсинг:

Общие:
- идентификатор трейсинга
- идентификатор пользователя
- идентификатор заказа
- timestamp
- система
- статус
- информация об ошибке

Internet Shop:
- размер 3D-файла
- время загрузки файла

Shop API:
- идентификатор созданного заказа
- статус сохранения в БД

CRM API:
- идентификатор сообщения в RabbitMQ
- данные синхронизации заказа

MES API:
- идентификатор оператора
- статус назначения заказа
- время обработки файла

RabbitMQ:
- количество in-flight сообщений
- время доставки между сервисами

Мотивация:

Внедрение трейсинга в указанных выше системах позволит быстро находить и устранять ошибки в процессе обработки заказов:
1. Клиенты жалуются менеджерам по продажам, что они не получили заказ - ошибка при сохранении заказа и потеря сообщений о новых заказах покажут путь проблемы и помогут устранить причины.
2. Представители компаний ежедневно сообщают, что не получили свои заказы - возможно сообщения не доставляются на производство, анализ полученных данных позволит выяснить причины.
3. Операторам важно видеть самые новые заказы, потому что от этого зависит их вознаграждение - анализ ошибок при назначении заказа оператору поможет выяснить детали.

Компромиссы:

Нужен будет ресурс команды разработки и как следствие снижение темпа реализации новых фичей, возможно временный полный отказ от реализации новых фичей в пользу реализации трейсинга.
Реализация трейсинга будет дорогой при больших объемах данных (высокая стоимость хранения данных).
Высокая стоимость для frontend.

Аспекты безопасности:

1. Ограниченный доступ к данным по модели RBAC
2. Использование TLS/SSL
3. Доступ к UI интерфейсу Jaeger только из корпоративной сети
